# Maintaining the Sector Tools

For anyone at Fast Forward who needs to change, add, or retire a tool. No prior context assumed.

## What this is

One repository for Fast Forward's coach-style tools. Each tool is a persona, a set of rules, a handful of prompts, and the reference files it reads. No app, no backend, no login. A tool runs inside the user's own Claude or Gemini, so Fast Forward never sees what anyone types.

## Layout

```
src/<tool>/            edit here
  tool.json            name, title, description, version, status, references
  persona.md           who the coach is and the rules for this tool
  prompts/NN-slug.md   one prompt per file
  knowledge/           reference files specific to this tool
src/shared/            the lens, the ethos, the playbooks; read by more than one tool
plugins/, dist/, .claude-plugin/   GENERATED by build.py. Never edit.
```

## One tool at a time

Each tool is sealed. Its prompts may read only its own `knowledge/` files and whatever `tool.json` lists from `src/shared/`. A prompt never names another tool; the persona may, once, to route a request that belongs elsewhere. Commands may share words across tools (Start, Grill, Run all) because each skill loads alone, but a prompt that starts talking about pitches inside the JD Builder is drift.

`build.py` enforces the first two rules and warns on the third. Beyond that: edit one tool per commit, and change `src/shared/` in a commit of its own, so a mistake in one tool's wording cannot be carried into another by the same edit.

## Standalone commands

A command whose input can be pasted (a PRD, an idea) can also ship as its own skill, so a user can run it cold in a new chat. Add two header lines to the prompt: `skill: <name>` and `input: <what it runs from>`. The build writes `plugins/<tool>/skills/<name>/SKILL.md` with the persona, the rules, and that prompt inline. The main skill keeps the command too. Wrap any persona text that only makes sense inside the main flow (orientation, step numbers) in `<!-- router-only -->` and `<!-- /router-only -->`. Standalone skills ship in the Claude Code plugin only; the zip stays one skill.

A command that depends on earlier steps in the same chat (Idea through PRD) stays in the main skill only.

## The edit loop

1. Change a file under `src/`.
2. Run `python3 build.py` (Python 3, no dependencies).
3. Commit everything, including the generated files. Users download from this repo.
4. For a release users should pick up: bump `version` in `tool.json`, rebuild, commit, and tag `v<tool>-<version>`.

## Adding a tool

This repository is public and holds only finished tools. A tool in progress lives in Fast Forward's private workshop repository until it passes the checklist below, then arrives here as one pull request: its `src/<tool>/` folder, any `src/shared/` file its `tool.json` lists, and the rebuilt generated files. Nothing else from the workshop comes across.

Copy an existing `src/<tool>/` folder, rename it (lowercase, hyphens), set `"status": "draft"` in `tool.json`, and build. A draft builds nothing and appears nowhere. Flip to `"public"` when it has passed the pre-publish checklist below.

A prompt with `internal: yes` in its header is for Fast Forward staff only. It is never published. Staff tools belong in a separate private repository, not here.

## Before a tool goes public

1. Every reference file is public-safe. Nothing in `src/` names a portfolio organization, a participant, a volunteer, or a partner company next to anything they said or paid.
2. Copy pass by MarComms on the README section and the persona.
3. An adversarial read by someone whose job is to find what is wrong.
4. A row in the Tools registry in Notion with owner, support tier, usage metric, sunset rule.

## Data

Raw inputs (Pitch Camp exports, survey responses) live in `src/<tool>/knowledge/raw/`, which git ignores. The published files are built from them with every name removed. The rule and the counts method are stated at the top of each built file.

## Updates reach users two ways

Claude Code users who installed from the marketplace get new versions automatically. Everyone who uploaded a zip stays on the version they uploaded until they download again. Keep prompts stable; put anything that changes often in a reference file, and say so in the release notes.
